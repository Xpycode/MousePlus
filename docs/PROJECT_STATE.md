### Ring UI redesign track (planned 2026-05-30)

Parallel to the HID work and not blocked by it. The user re-imagined the menu as a **concentric wedge ("pie") menu**: inner symbol ring + middle labeled ring sharing locked spokes, plus an on-demand outer ring that expands as a localized arc from a parent wedge, with focus-dimming of inactive branches. Full spec + 12-task/5-wave breakdown in `IMPLEMENTATION_PLAN.md`; design rationale in `decisions.md` (2026-05-30 "Ring UI: Concentric Wedge Menu"). Replaces the current circles-in-a-ring `RingMenuView`; reuses triggers, NSPanel, `RingMenuItem`, `ActionService` untouched.

**🅞 Open design direction — selectable interaction/layout model (raised 2026-05-31-b):** rather than committing to one menu style, make the **interaction/layout model a user choice** ("different people, different muscle memory"). Candidate models:
1. **Concentric 3-ring** (current) — see two levels at once, pointer-anchored.
2. **Drill-down / marking-menu** — one active ring; selecting a wedge makes the current ring recede and a **new ring appears localized around the just-chosen wedge**, recursively, so the next command is always ~the same distance/direction away (consistent muscle memory; cf. Maya/Blender marking menus). Trade-off: loses "see two levels at once." Born from the observation that the outer (3rd) ring is large/far and feels cumbersome to navigate.
3. **Stream Deck-style grid** — fixed rows×cols of large labeled buttons, learned by position; likely a *different summon model* (fixed location / persistent vs. at-cursor). Less radial-muscle-memory, more glanceable.
4. **A novel model after research.**

**Architecture note:** the data model (`RingMenuItem`/`Configuration`) is already layout-agnostic; layout-specific code is concentrated in `RingMenuView` (render), `RadialGeometry` (hit-test), and `commitActive`/`expand` in `RingViewModel`. The seam would be a `MenuStyle`/`InteractionModel` protocol those three plug into, chosen in Settings. **Risk = premature abstraction:** designing that protocol across models that don't exist yet would guess wrong (grid wants pages/columns; drill-down wants a nav stack; ring wants angular spans). **Recommended sequencing:** finish more real action features first, then prototype the **drill-down model as a second renderer behind a flag** — building the *second* layout reveals the true protocol; Stream Deck + researched models then drop into a proven seam. Ship a "choose your model" setting only once ≥2 exist. Not scheduled. Full write-ups in sessions `2026-05-31-b.md`.
