### Discovered: Karabiner-Elements DriverKit blocks extended mouse buttons

This is the W3 verification story. We attempted multiple test triggers in sequence and each surfaced a different lesson:

1. **Mouse button 3 (back, MX Master)** — never fired. Suspected Logi Options+; user clarified they use BetterMouse, not Logi
2. **Switched to button 5** ("Do Nothing" in BetterMouse, theoretically passes through) — also nothing. Discovered "Do Nothing" in BetterMouse means "BetterMouse takes the input and does nothing with it," not "pass through to macOS"
3. **Quit BetterMouse + Karabiner-Elements UI** — still nothing. `ps -axc` revealed Karabiner-DriverKit-VirtualHIDDevice (PID 290) and friends still alive (system extensions don't quit when the menu app does)
4. **Right-click + middle-click sanity check** — `R-down button=1` and `O-down button=2` came through cleanly via NSEvent. So buttons 0/1/2 work; 3+ are eaten

**Root cause:** Karabiner installs a DriverKit virtual HID device that all mouse input flows through. Standard buttons (0/1/2) pass through; extended buttons (3+) are filtered, even with no Karabiner rules active. NSEvent global monitors sit *behind* DriverKit drivers (`kCGTailAppendEventTap`, listenOnly), so they only see the post-driver output. BetterMouse uses `CGEventTap` at session level — sits *in front of* DriverKit, sees everything.

**User confirmed Karabiner is unused on their system** — installed at some point, no rules, doesn't remember why. Decided to uninstall.

### Decisions Made

- **Tap-toggle interpretation lives at the AppDelegate (consumer) layer**, not in TriggerService. Service emits raw `.down`/`.up` carrying the configured mode; only the consumer (which knows ring-visibility state) interprets. Keeps the service mode-agnostic and reusable.
- **Build Identify Input as a permanent feature**, not throwaway diagnostic. Same UI shape that W4 needs anyway, and a lasting power-user diagnostic for "why isn't my trigger firing" support cases.
- **Defer mouse-button end-to-end verification** until user finishes Karabiner uninstall + reboot. Architecture is provably correct (left/right/middle clicks all flow correctly); the blocker is purely environmental.
- **Plan v1.1 CGEventTap upgrade** for production. Power-user audience commonly has DriverKit-based input customizers (Karabiner, etc.); NSEvent global monitors are insufficient. Saved as memory `karabiner-driverkit-mouse-interception` for future sessions.
- **Test default temporarily set to button 2 (middle-click) + Numpad-Clear (tap-toggle)** so the user can experience both pipelines in the meantime. Replaced after Karabiner uninstall with whatever real button the user prefers.

## Notes

- Adding the `setvbuf(stdout, nil, _IONBF, 0)` to `MousePlusApp.init` proved essential for diagnostic captures: when launched as a backgrounded subprocess with redirected output, stdout block-buffering otherwise hides print output until the buffer fills (~4KB). Pattern worth keeping bookmarked.
- The user's setup (BetterMouse + Karabiner + Alfred + Raycast) is genuinely common for the target audience. Every interceptor we documented (Karabiner-DriverKit, BetterMouse "Do Nothing", Logi Options+ Spotlight collision, vendor-mapped buttons) has a corresponding W4 onboarding warning we should ship. The Identify Input window is the runtime mechanism for catching most of them: if a recorded binding produces no captured event, an interceptor is the prime suspect.
- AppDelegate `triggerEventTask` is now mode-aware. W4 doesn't need to touch the consumer logic at all — adding new bindings just means letting the user record a `TriggerBinding` value and writing it into config.
