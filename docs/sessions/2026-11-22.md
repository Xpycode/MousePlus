# Session 2: 2026-11-22 (App HUD inheritance spec and plan)

## Goal

Turn the "App HUDs inherit from Global" decision into an approved spec and an executable plan.

## Progress

- Wrote `specs/app-hud-inheritance.md` (status: Approved). It has 19 acceptance criteria plus
  AC12a and AC12b. Design choices, all confirmed by the user:
  - App items stay linked to Global items by item ID.
  - An override covers the whole item. There is a **Customize** button, and **Revert to Global**.
  - Items added to or deleted from Global follow through to App HUDs. An item the app had
    customized is kept as app-only.
  - An app can give a ring its own order, with **Revert Order** placed after Move Later.
  - Deleting an inherited item in an app hides it, and it can be restored from **Hidden Items (N)…**.
  - When a ring has more than 8 items, Settings warns "Not enough space"; the HUD shows the
    first 8.
  - Test Action names where the item comes from.
  - Older builds are not supported. They fall back to Global for the new entries, which is
    harmless.
- Ran two agents. A code survey mapped every affected file and the save and guard path. Web
  research covered Xcode, Figma, VS Code, Kubernetes strategic-merge patches and the JSON patch
  RFCs, and recommended storing only the differences, keeping deletion markers, and anchoring
  app-only items to the item before them.
- Wrote `docs/plans/app-hud-inheritance-implementation.md`: 11 tasks in 5 waves, plus E1 (Atlas
  Settings check) and E2 (user live acceptance). Linked it from PROJECT_STATE and from TASKS under
  Active plan.

## Decisions

- These are all recorded in the spec and plan, and they extend the existing 2026-11-22 entry in
  `decisions.md` (no new ADR):
  - Sparse storage, with older builds unsupported.
  - Deterministic overflow at 8 items.
  - New Global items go at the end of custom-order rings.
- Research flagged that prior art overrides single fields. The user's whole-item choice stands.
  This was surfaced in chat; the user can revisit it.
