### MX4 capture #1 (selective matching, Inspector schema v2)
- File at repo root: `hid-046d-b042-1x2-2026-05-02.json`. 62 elements, 80 live captures, **0 raw reports**, no fire-count field.
- Initial analysis was misleading: only 1 button event in `liveCaptures` (the Save click itself). Made it look like the MX4 was as silent as the 3S.
- Investigation: `liveCaptures` is a global ring buffer capped at 80 entries; with mouse motion + AC pan it fills with ~1 second of motion data and evicts every button press that came earlier. The snapshot file was lying through omission.

### Inspector fixes (schema v3)
Three real bugs fixed in `IOHIDDeviceInspector` + `HIDDeviceSnapshot`:

1. **`fireCounts` not in JSON** — the Inspector tracked per-element accumulated fire counts in memory and showed them as orange ×N badges in the UI, but `snapshot(for:)` dropped them. Added `HIDFireCount` struct + `fireCounts: [HIDFireCount] = []` field; populated from `fireCountsByDevice` joined with `elements`, sorted by count desc.
2. **`liveCaptures` was global + tiny** — replaced single `lastFires: [HIDValueCapture]` (cap 80) with `lastFiresByDevice: [HIDDeviceInfo.ID: [HIDValueCapture]]` (cap 10 000 per device). Snapshot now reads its device's exact ring instead of best-effort filtering by cookie. Removes cookie-overlap risk between devices.
3. **`rawReports` cap too small** — bumped 40 → 1 000 per device.

Also added `matchAllDevices: Bool?` to the snapshot for capture-time provenance, and bumped `schemaVersion` to 3. Old v2 files still decode (new fields have defaults / are optional).

**Page `0xFF43` (HID++ vendor pipe) fires — six vendor cookies live:** 17 (12), 22 (8), 26 (4), 19 (3), 25 (3), 21 (2). The MX4 firmware emits HID++ traffic *without* an explicit divert from us. This is materially different from the MX3S behaviour observed in session-e ("firmware-withheld until ReprogrammableKeysV4 set").

**`rawReports` still 0** despite the buffer fix. Most likely the standard mouse interface (`primaryUsagePage=1, primaryUsage=2`) delivers parsed element values for vendor-page elements but routes the underlying `0x11` long-format reports to a *separate* HID interface of the same physical device — which, with match-all on, should appear as another picker row (e.g. with primary `0xFF43`). User did not capture from the alternate interface this session.

### Discovered

- **Per-product variance is real and goes deeper than expected.** MX3S vendor page = `0xFF03`, MX4 vendor page = `0xFF43`. MX3S firmware withholds without divert, MX4 firmware emits some traffic by default. Plan B's HID++ implementation must discover the vendor page per-device and not assume a single byte sequence works across products.
- **Session-e's "firmware-withholds-everything" conclusion for the MX3S is now suspect.** That snapshot was schema v2 with the same 80-entry global ring and no per-element fire counts. We may have drawn the wrong conclusion from a lossy snapshot. A re-capture of the MX3S with the v3 Inspector is worth doing on the M1 Max.
- **The Inspector exposes multi-interface devices as separate picker rows** when match-all is on. This is correct (Logitech splits standard mouse vs vendor pipe across interfaces), but means a "complete" snapshot of one physical device requires capturing each interface separately.

### Decisions Made

- **No HID++ strategy decision yet.** Evidence shifted in favour of option 2 (implement HID++ host-side): the MX4's vendor pipe is already alive, so we wouldn't be starting from zero traffic. But still deferred — capture #3 from the alternate MX4 interface needs to land first to confirm raw-report bytes are reachable.
