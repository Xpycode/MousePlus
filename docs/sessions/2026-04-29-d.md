### Pivot — IOHIDManager backend for the mouse-button monitor

User pointed out that **BetterMouse sees those events** on this same machine. So they're reachable from userspace; NSEvent is just too high-level — Logitech ships those buttons on the HID consumer page (and possibly vendor-specific reports), which `NSEvent.otherMouseDown` doesn't surface.

**Decision (D4):** swap `MouseButtonTriggerMonitor`'s NSEvent backend for an **IOHIDManager** backend. MousePlus's pitch is "made for MX Master owners," and the thumb button + wheel-mode button are exactly the triggers a power user wants — shipping without them undermines the value prop.

- **Cost estimate:** ~150–250 lines for a focused mouse-button HID monitor that maps HID usages → existing `TriggerBinding.mouseButton(Int)` enum.
- **Permissions:** Input Monitoring only (already granted) — no DriverKit, no extra entitlements.
- **Architecture:** sits behind the existing `TriggerMonitor` protocol; `TriggerEvent` stream + AppDelegate stay untouched.
- **Side effect:** likely **retires the v1.1 CGEventTap plan** for Karabiner-coexistence — IOHIDManager reads from the physical device before the event subsystem layer Karabiner's virtual HID intercepts at.

**Approach: A then B** (user choice).

- **A — IOHIDDeviceInspector first.** Small utility that enumerates connected HID mouse devices and dumps every input element with `usagePage` + `usage` + cookie. Drop into the Identify Input window as a "HID elements" panel. Gives a precise, runtime map of what *this user's specific MX Master 3S* exposes before we commit to the monitor's API surface.
- **B — Then build the monitor** based on what A reveals, using standard HID Button + Consumer pages plus any vendor specifics found in the dump.
