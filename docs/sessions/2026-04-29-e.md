### IOKit dispatch-queue traps hit during bring-up (all fixed)

Each was a real assert with a crash report; cataloguing because the dispatch-queue mode is a minefield and these will bite again:

1. **`Open` after `Activate` asserts** "Device has already been activated/cancelled." Fix: `Open` first, then `Activate`. (The header docs *don't* spell this out clearly.)
2. **`IOHIDManagerRegister*Callback(mgr, nil, nil)` post-Activate asserts** the same way. You cannot un-register callbacks once activated. Fix: drop the unregister calls in `stop()`; just call `Cancel` (only if state was actually running).
3. **`IOHIDDeviceRegisterInputReportCallback` from a hot-plug device-matching callback asserts.** The matching callback fires post-Activate, so the device is already activated when handed to us. Fix: pre-register input-report callbacks **between Open and Activate** via `IOHIDManagerCopyDevices`. Hot-plug arrivals don't get raw-report capture — accept the limitation.
4. **`IOHIDManagerOpen` with match-all returns `kIOReturnUnsupported` (0xE00002C7) from system-claimed devices** (touchbar, builtin sensors, etc.). One bad apple sinks the whole `Open`. Fix: only treat `kIOReturnNotPermitted` as fatal; surface anything else as `runningPartial` and Activate anyway — devices that opened still fire callbacks.

## Discovered — and this changes plan B

The earlier session-d hypothesis "Logitech ships those buttons on the HID consumer page" was **partially right but missed the deeper truth**. With BetterMouse and Logi Options+ both quit, with match-all enabled, with raw-report capture wired up: pressing DPI / thumb / gesture buttons produces **zero HID traffic at any layer**. Not buried in a vendor report we missed — *the mouse never transmits anything at all*.

Why: MX Master 3S firmware ships those buttons in a **"diverted, awaiting host query"** state. They only emit events after the host issues a HID++ 2.0 `ReprogrammableKeysV4` (feature `0x1B04`) "set divert" command on the vendor pipe (output reportID 0x11 → page 0xFF03). Logi Options+ does this on startup. Without it, the buttons are firmware-silent.

So macOS isn't filtering; IOHIDFamily isn't eating vendor reports for HID++ devices. The mouse is simply withholding the events. This is what `logiops` (Linux) and `Mouser` (macOS) work around by speaking HID++ themselves.

## Blockers

None technical. **One product decision needed before plan B starts** — three options laid out:

1. **Accept the limitation.** Document "DPI / thumb / gesture require Logi Options+ running." Undercuts the "made for MX Master" pitch.
2. **Implement HID++ 2.0 host-side.** ~200 lines of well-understood protocol code. Sends the right `0x11` output reports at startup to enable button events on the vendor pipe. Works on both BLE and Bolt-receiver MX Masters. No Options+ dependency. The `logiops` / `Mouser` path.
3. **Coexist with Options+.** Read events Options+ has already enabled. Fragile — Options+ also consumes presses for its own remapping.

User to choose before plan B. Recommendation: option 2 (matches the product positioning).
