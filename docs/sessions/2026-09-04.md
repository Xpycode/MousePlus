## Decisions

- Reveal remains visible until the HUD invocation closes. Immediate mouse-exit collapse was rejected because normal travel from a parent toward its outer child would make the arc unstable.
- Reveal is genuinely hover-driven: center-to-parent traversal opens the branch without click or release; Always retains deliberate click/release expansion and Hidden never exposes the branch.
- Hold-release commits from the trigger event's pointer snapshot rather than callback timing or stale SwiftUI hover state.
- Label visibility and orientation resolve as a presentation-layer pure function decoupled from the persisted model type, so the parallel model (1.1) and presentation (1.2) tasks needed no reconciliation once both landed — `LabelPresentationPolicy` binds directly to the model's `LabelOrientation`.
- The Menu/Inner/Middle/Outer customization tab is intentionally separate UI state from `model.activeBand`, per the Wave 1 Operational Learning that the Menu Items band selector must never be silently retargeted by browsing ring settings. It is not lifted into `MenuEditorModel`; it resets to the Menu tab whenever the outer "Menu & Rings / Selected Item" inspector switch leaves and returns, which is acceptable since no acceptance criterion requires it to persist.
- Task 3.2 needed no production code: `hudCustomization` (and therefore its new label fields) was already carried as one Codable struct through `merged(into:)`, the coordinator's field-based dirty/merge/save machinery, and reset/undo/backup-restore — none of it decomposes into individual sub-fields. Verification work belonged entirely in tests, not implementation.
- Help/Feedback/Tip/Appearance belong in Settings (a new "About" sidebar section), not the status-item menu — MousePlus is `LSUIElement`-only with no traditional app menu bar to hang them on.
- The new Appearance picker (app-chrome Light/Dark/System) is deliberately scoped to the Settings window only; it must not touch or be conflated with the per-ring HUD colors already signed-live-verified in Ring Appearance.
- Feature C (app switcher) and Feature A (menu mirror) share one `DynamicSource`/async-`expand()`/`IconSource` foundation; whichever feature is implemented first builds it, the other consumes it unchanged — do not fork a second implementation.
- System toggles use a curated `enum` dispatched via `Process` → `/usr/bin/osascript` (never `NSAppleScript`, never reusing the free-form `.custom` shell path) specifically so the one interpolated argument (volume level) can be validated and the injection surface stays closed.
- `AppSwitcherService` reuses `.appSwitch`'s existing commit path unchanged — population is the only new surface; `ActionService.execute` needs zero changes.
- `expansionEpoch` is an incrementing counter, not a boolean, because hover-driven Reveal can re-point from one dynamic wedge straight to another mid-fetch — a boolean can't distinguish "still the same expansion" from "briefly neither old nor new" during that transition.
- `RingMenuItem.hasSubItems` now means "expandable" (static sub-items OR a non-`.none` `dynamicSource`), not just "has a populated `subItems` array" — every future `dynamicSource` case (e.g. Feature A's menu mirror, if it lands with its own dynamic arm) inherits correct expand/execute/chevron/warning behavior automatically as long as it goes through this property rather than checking `subItems` directly.
