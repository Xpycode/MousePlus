## Design idea logged (not yet a decision) — "drill-down / marking-menu" ring navigation
While using the working snap feature, user noted the **third (outer) ring** is large and far
from center, so drilling in + selecting feels cumbersome. Proposed alternative to the static
3-ring concentric layout:

- Show **one active ring** at a time.
- Selecting a wedge → the current ring recedes/"slightly vanishes" and a **new ring appears
  localized around the wedge just chosen**; repeat for deeper levels.
- Payoff: the next command is **always ~the same distance and direction away** from where the
  cursor just acted → consistent gesture rhythm / muscle memory (cf. Maya/Blender marking
  menus, Alias radial breadcrumbs).
- Trade-off: loses the concentric design's "see two levels at once"; gains shorter travel +
  consistency. Directly targets the observed outer-ring friction.

Captured here + flagged in PROJECT_STATE (Ring-UI track) as an open design question. Not
scheduled; revisit before investing further in deep outer-arc interactions.

### Follow-on idea — selectable interaction/layout model (umbrella)

**Architecture read (logged so we don't over-build):** the data model
(`RingMenuItem`/`Configuration`) is already layout-agnostic; layout code lives in
`RingMenuView` (render) + `RadialGeometry` (hit-test) + `commitActive`/`expand`
(`RingViewModel`). A `MenuStyle`/`InteractionModel` protocol could let those plug in,
selected in Settings. **But** extracting that seam now — across models that don't exist —
would guess the interface wrong (grid wants pages/columns; drill-down wants a nav stack;
ring wants angular spans). **Recommended sequencing:** finish more action features, then
build the **drill-down model as a second renderer behind a flag** (the second layout reveals
the real protocol); Stream Deck + researched models drop in afterward; ship the "choose your
model" setting only once ≥2 exist. Not scheduled.

## Goal realignment (end of session) — make inner + middle rings customizable
User paused to set the north star: **inner and middle rings should be user-customizable, with the
outer ring reacting to the middle ring.** Ground-truthed against the code:

- **"Outer reacts to middle" already exists.** `innerItems`/`middleItems` are independent action
  sets sharing only spoke geometry; `outerItems = middleItems[selectedWedge].subItems`. Inner
  items are **direct-only** (never expand an outer ring). So the architecture already matches the
  goal — no behavior change needed here.
- **"Customizable" is the real gap.** The Settings **"Menu Items" tab is a stub**
  (`MenuSettingsView` = `Text("Menu item customization coming soon")`). Today the only way to edit
  either ring is hand-editing `config.json` (as done this session to inject the Snap wedge). So the
  work the goal implies = **build the Menu Items editor.**

Editor scope sketch (for next session): per item — label, SF-Symbol icon, action type, and
**action-type-aware data** (app picker for `appSwitch`, command field for `custom`, `SnapZone`
picker for `windowSnap`; menuBar/systemToggle/screenshot later); add/remove/reorder; surface the
8-spoke cap (`N = min(8, max(inner, middle))`) and inner↔middle alignment; per-middle-wedge
`subItems` editing (= the outer ring). Live-apply via a new `AppDelegate.applyMenuItems` hook
(mirror `applyAppearance`) + debounced `ConfigurationService.save` (mirror
`RingAppearanceSettingsView`). Open question to user: confirmed the only gap is the editor UI (model
+ outer-reacts-to-middle already correct); awaiting go-ahead to draft a plan.

## Menu Items editor — plan drafted (research-backed) → `docs/MENU_EDITOR_PLAN.md`
Drafted a full plan via 4 parallel research agents (codebase scout · SwiftUI-macOS patterns ·
the two hard pickers · competitive-UX), MCP Apple docs, and the web. **User decided the layout:**
a **dedicated, resizable editor window, WYSIWYG-lite** — a live ring preview you *click to select a
slot*, with a detail form below (not in-tab; the 460×460 pane is too small. not drag-on-canvas; no
shipping radial app does that). Key research-backed calls baked into the plan:
- **Bind by identity, never index** (id-keyed safe-subscript bindings + `ForEach($array)`) —
  structurally prevents a repeat of the 2026-05-31 outer-band index-out-of-range crash class.
- **`RingMenuItem` stays a struct** (no `@Observable`-class conversion); editor edits working
  copies + live-applies via a new `AppDelegate.applyMenuItems` hook + debounced autosave (mirrors
  the appearance tab).
- **SF Symbol picker**: the "built-in `SymbolsPicker`" claim was FALSE (it's a 3rd-party package);
  v1 = zero-dep curated grid + `NSImage(systemSymbolName:)` validation (blocks blank wedges).
- **App picker**: non-sandboxed scan of `/Applications` + running apps, store **bundle ID**,
  `NSOpenPanel(.application)` fallback; avoid deprecated LaunchServices calls.
- **Found gap:** `appSwitch` wedges render an SF Symbol, *not* the real app icon, until
  `IconSource`/Feature C ships — editor sets expectations; model unchanged for the future flip.
Plan = 12 tasks / 5 waves (model+hook → pickers → editor shell → window+persistence → invariants +
user-driven verify), ≈3–4 dev-days. Risks + decisions-to-log in the doc. **Not yet built.**
