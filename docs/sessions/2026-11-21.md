## Progress

1. **Key labels follow the keyboard layout (fixed, user-confirmed in screenshot: `Shift+Cmd+#`).**
   `Utilities/KeyCodeNames.swift` now asks the current layout (`TISCopyCurrentKeyboardLayoutInputSource`
   + `UCKeyTranslate`, display action, no-dead-keys mask, `LMGetKbdType`), with fixed labels for
   non-printing keys, a "Keypad" prefix for keypad keys, and the US table as fallback. Main-thread only.
   - Correction to the 2026-11-18 note: the Send Keystroke row was already layout-aware through
     ShortcutKit; the US-only table was the Triggers tab. The Send Keystroke row had a different
     mislabel (ShortcutKit's letter rule would show a German Z key as Y, because MousePlus stores
     physical key codes). `ActionDataEditor.committedKeystrokeDisplay` now uses the same positional
     label as Triggers; visible change: text modifiers (`Shift+Cmd+#`) instead of glyphs.
   - New `MousePlusTests/KeyCodeNamesTests.swift` (8 tests).
2. **Stale Menu Items preview (precaution only; cause not reproduced).** A read-only diagnosis found
   no path where a loaded editor holds sample items while status is "Saved". Most likely only the
   preview's private `RingViewModel` stayed on its seed samples when Settings opened directly on Menu
   Items. `MenuItemsPane` now remounts the editor when loading finishes (`.id(coordinator.isLoaded)`).
   The new regression test `testPreviewFollowsALoadThatLandsImmediatelyAfterMount` passes even
   without the fix, so the race is unconfirmed. If it recurs: check the Selected Item tab before
   clicking the ring; real items there means only the drawing is stale.
   - Verified hazard, not fixed: a Menu Items save replaces the whole Global menu on disk
     (`SettingsWorkspaceCoordinator.merge`, `base.inner = edited.inner`) with no changed-externally
     check, unlike app HUDs. No second writer exists today. Added to Backlog.
3. **Send Keystroke from the ring did not reach Safari (fix built, live acceptance pending).**
   Symptom: system sound, or the MousePlus Settings window coming forward. A passive frontmost-app
   logger showed MousePlus becoming the active app right after ring use in Safari (16:21:40, 16:21:54),
   so the chord went to MousePlus. The synthetic event itself is correct (inspected, not posted).
   Earlier live checks used the keyboard hold-release route, where nothing is clicked.
   - `RingHostingView`: `shouldDelayWindowOrdering` returns true and `mouseDown` calls
     `NSApp.preventWindowOrdering()`. Why the non-activating panel activates on click is not
     established; this part is unverified.
   - `ActionService`: for live-ring keystrokes (`ActionContext.returnsFocusToTarget`, set by
     `RingViewModel`), if MousePlus is frontmost it yields activation to the target PID and waits up
     to 0.5 s for it to be frontmost before posting. Settings "Test Action" is unchanged.
   - Two new tests in `ActionServiceTests`.
